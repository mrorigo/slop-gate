# P9.4 structural-erosion calibration plan

Status: runner implemented; preliminary panel run completed.

## Objective

Calibrate `structural-erosion` defaults and warning levels against real Rust
repository history. The calibration must measure normal repository variation,
known refactoring events, and the actionability of reported contributors.

The result is not a ranking of repositories. It is evidence for these policy
questions:

1. What erosion ratio is common in maintained Rust repositories?
2. What erosion delta is unusual for a normal commit or release window?
3. Does the reported contributor identify the code reviewers would inspect?
4. Which `complexity_cutoff` values produce stable, useful findings?

Do not promote `structural-erosion` to `error` based on this study alone.

The panel deliberately mixes libraries, binaries, frameworks, macro-heavy
projects, and large workspaces. Tokio, Clap, Rayon, and ripgrep are suitable
initial anchors because their project pages identify them as established Rust
projects with distinct workloads; the remaining panel prevents conclusions from
depending on one architecture style. For example, Clap reports more than
16,000 GitHub stars and 320 releases, while Rayon describes a focused parallel
iterator library. These are selection signals, not quality labels. See the
[Clap repository](https://github.com/clap-rs/clap),
[Rayon repository](https://github.com/rayon-rs/rayon), and
[ripgrep repository](https://github.com/BurntSushi/ripgrep).

### Inclusion rules

Include a repository only when all conditions hold:

- the canonical repository is publicly cloneable;
- Rust is a primary implementation language;
- the default branch has at least 24 months of history or 100 commits;
- the repository has at least 10 commits in the selected 12-month window;
- its license permits local source analysis;
- its checkout can be analyzed without network access after cloning.

Record exclusions and replacements in the manifest. Do not silently replace a
repository because it is too large or produces inconvenient analyzer errors.

## Sampling design

Analyze one full baseline and 12 monthly checkpoints for each repository when
history permits. Use the first-parent chain of the default branch. Select the
checkpoint closest to the first day of each month, preserving chronological
order. Also sample 20 individual commits per repository from the same window:

- 10 uniformly spaced commits;
- 5 release-tag commits when tags exist;
- 5 commits selected from high-churn windows.

The monthly series measures drift. The individual commits measure gate-sized
changes. Avoid using only release commits because release engineering can
distort source metrics.

For each sampled revision, record:

- repository and commit ID;
- commit date and parent ID;
- analyzed Rust file count and function count;
- total mass;
- high-complexity mass;
- erosion ratio;
- high-complexity function count;
- maximum CC and maximum function mass;
- analyzer version, artifact schema, policy, and cutoff;
- analysis duration and operational result.

For each sampled commit after its parent, record the erosion delta and the
top three contributors. A commit with malformed source is recorded as an
analysis failure and excluded from threshold fitting, not silently treated as
zero erosion.

## Temporary checkout workflow

Run the suite from a clean directory outside the Slop Gate repository. The
workflow must not modify the source repositories or use their build systems.

1. Create a temporary root with `mktemp -d`.
2. Clone each pinned repository with full commit history.
3. Resolve and record the default branch and selected commit IDs.
4. Run the pinned Slop Gate binary from each repository root.
5. Write one JSON document per repository and checkpoint.
6. Write stderr and exit status beside each result.
7. Remove the temporary root after result verification.

The first implementation should use the existing command:

```sh
slop-gate history --ref <commit> --count <N> --format json
```

For commit-level deltas, run `history` over a bounded window ending at each
selected commit, or add a dedicated machine-readable parent/head sampler if
the repeated history scans exceed the performance budget. Do not use
`cargo run` in the calibration suite. Build and pin one Slop Gate binary before
the run.

Recommended suite inputs:

```text
manifest.toml
output/<repository>/history.json
output/<repository>/commits.jsonl
output/<repository>/stderr.log
output/manifest.lock
```

`manifest.lock` must contain repository URLs, resolved commit IDs, Slop Gate
version, analyzer fingerprint, policy fingerprint, cutoff, host target, and
UTC start time.

## Calibration policies

Run at least these analyzer configurations over the same samples:

```toml
[rules.structural_erosion]
severity = "warn"
erosion_limit = 0.50
delta_limit = 0.08
complexity_cutoff = 10
top_contributors = 3
```

For sensitivity analysis, vary only `complexity_cutoff` across `5`, `10`, and
`15`. Do not fit thresholds and cutoff simultaneously without recording the
multiple-comparison decision.

The suite must not use repository-specific suppressions during threshold
fitting. Suppressions hide the observations needed to judge the rule.

## Analysis

Calculate results per repository and for the pooled panel. Report medians,
quartiles, 90th, 95th, and 99th percentiles for erosion ratios and deltas.
Report distributions separately for libraries, applications, and workspaces.

Classify each delta finding by inspecting the commit subject, changed paths,
and contributor location:

1. expected maintenance;
2. deliberate refactoring;
3. feature growth;
4. generated or scope artifact;
5. analyzer defect;
6. actionable complexity concentration.

The evaluator must record the classification and a short reason. A high ratio
without a positive delta is background repository state, not a regression.

Evaluate contributor stability by checking whether the top contributor remains
in the top three across adjacent monthly checkpoints. Record the percentage of
findings where a reviewer would inspect the reported location first.

## Threshold decision

Choose defaults only after all of the following are available:

- a target of 20 repositories, with at least 15 repositories with valid
  results accepted when every shortfall is documented;
- at least 150 commit-level samples across the panel, with 10 samples per
  valid repository when fewer than 20 repositories complete;
- at least 30 classified erosion findings, if the panel produces that many;
- a written explanation for every excluded repository and failed sample;
- separate results for each cutoff value;
- reviewer actionability for every proposed warning threshold.

Keep the rule warning-only when the panel contains fewer than 30 findings or
when analyzer defects exceed 5% of findings. Do not promote to `error` when the
95th-percentile normal delta overlaps the proposed blocking threshold.

The calibration report must publish the chosen `erosion_limit`,
`delta_limit`, and `complexity_cutoff`, plus the number of warnings that would
have appeared under each candidate policy.

## Deliverables

Create these files after execution:

- `docs/EROSION-CALIBRATION-REPORT.md` with methods, pinned commits,
  distributions, classifications, and policy decision;
- `calibration/manifest.toml` with repository URLs and resolved commits;
- `calibration/results/` containing immutable JSON outputs;
- `calibration/README.md` describing reproduction and tool versions;
- a suite script or Rust test harness that validates result schemas and
  deterministic reruns.

Do not commit cloned repositories or generated checkout contents.

## Acceptance criteria

| Area | Criterion |
| --- | --- |
| Panel | 20 repositories are targeted; at least 15 satisfy the inclusion rules or have documented replacements. |
| Reproducibility | A second run with the same manifest and binary produces identical normalized JSON. |
| Coverage | At least 200 commit-level samples are targeted; at least 150 and 12 monthly checkpoints per eligible repository are required for a reduced panel. |
| Isolation | Every repository is analyzed in a temporary checkout without source or build-system changes. |
| Accounting | Every sample records commit, parent, analyzer fingerprint, cutoff, duration, status, and summary facts. |
| Classification | Every erosion finding has a reviewer classification and reason. |
| Decision | Thresholds are chosen from panel distributions and documented with alternatives. |
| Rollout | `structural-erosion` remains warning-only unless the documented evidence supports promotion. |
| Verification | Slop Gate tests, schema validation, and `git diff --check` pass. |

## Current status

The runner, manifest, aggregation command, and temporary-checkout workflow are
implemented. A preliminary run attempted all 20 repositories and produced 200
valid commit samples across 10 repositories. The results are in
`calibration/results/`, with pooled statistics in `calibration/analysis.json`.
The run is insufficient for threshold calibration because it does not yet have
20 valid repositories, monthly and release sampling, cutoff sensitivity output,
top-contributor extraction, reviewer classifications, or deterministic rerun
comparison. The rule remains warning-only until those gaps are closed.
