# Slop Gate v0.4 plan

Status: planned.

This plan extends the existing Rust-only, Git-revision-based gate. It adds
repository-level complexity concentration measurements and a history view. It
does not make a heuristic an error by default.

## Product outcome

Version 0.4 answers two questions:

1. Did the change increase the share of complexity mass held by high-complexity
   functions?
2. Which functions account for that change?

`check` continues to evaluate a base revision and a head revision. `index`
continues to create an artifact for one exact commit. Existing rule behavior,
exit codes, report formats, and artifact validation remain compatible unless
the artifact schema version changes as specified below.

## Scope

### Included

- A `structural-erosion` rule.
- Repository-wide erosion facts in index artifacts.
- Base-to-head erosion comparison during `check`.
- Deterministic attribution to the largest contributing functions.
- Human, JSON, and SARIF output for erosion findings.
- A multi-revision history command or mode for trend inspection.
- Calibration against maintained Rust repositories.
- Documentation and tests for all new configuration and output fields.

### Deferred

- A general AST-based `verbosity` rule.
- LLM, embedding, or semantic-equivalence analysis.
- Cross-language erosion comparisons.
- Module-level erosion as a gate condition.
- Automatic refactoring suggestions.
- Error-level defaults for `structural-erosion`.

The existing `near-clone` rule remains the first implementation of structural
duplication detection. A later duplicate-mass or clone-ratio metric may reuse
its clone-family facts, but is not required for v0.4 acceptance.

## Definitions

| Term | Definition |
| --- | --- |
| Function mass | `CC × √SLOC`, using the existing analyzer facts. |
| High-complexity function | A function whose `CC` is greater than `complexity_cutoff`. |
| Total mass | The sum of function mass for all analyzed functions in a revision. |
| High-complexity mass | The sum of function mass for high-complexity functions. |
| Erosion ratio | `high_complexity_mass / total_mass`. |
| Erosion delta | `head erosion ratio - base erosion ratio`. |
| Contributor | A head function that is newly high-complexity or increased its mass while high-complexity. |

Functions excluded by the existing analyzer scope do not contribute to any
erosion value. A revision with no analyzed functions has an erosion ratio of
`0.0`. A revision with analyzed functions but zero total mass is invalid
because every function has at least `CC = 1` and positive SLOC under the
existing extraction contract.

## Configuration

Add the following section to `.slop-gate.toml`:

```toml
[rules.structural_erosion]
severity = "warn"             # off | warn | error
erosion_limit = 0.50           # 0.0 <= value <= 1.0
delta_limit = 0.08             # value >= 0.0
complexity_cutoff = 10         # CC > this value is high-complexity
top_contributors = 3           # 1..=10
```

The default severity is `warn`. The default limits are provisional and must be
calibrated before release. Missing configuration uses these defaults. Unknown
keys, non-finite values, out-of-range ratios, zero contributor limits, and
cutoffs that do not fit the supported integer type are operational errors with
exit code `2`.

The new rule participates in the policy fingerprint. Changing any of its
values requires a new baseline artifact.

## Artifact changes

Add these facts to the artifact's repository summary:

```text
total_mass: f64
high_complexity_mass: f64
erosion_ratio: f64
high_complexity_function_count: usize
maximum_function_cc: u32
maximum_function_mass: f64
```

Retain the existing per-function `sloc`, `cc`, and `mass` facts. Store the
analyzer representation version and `complexity_cutoff` used to calculate the
summary. Bump the artifact schema version if the current schema cannot safely
represent these fields. Older artifacts must fail with an actionable version
error; no implicit migration is required.

Artifact facts must be finite, deterministic, and derived only from the exact
indexed Git commit and analyzer inputs. They must not contain source text.

## Gate behavior

For `check --base B --head H --index A`:

1. Validate the artifact, repository identity, base commit, analyzer version,
   and policy fingerprint.
2. Analyze the head revision using the same scope and cutoff as the artifact.
3. Compute the head repository summary.
4. Emit one `structural-erosion` finding when `head erosion ratio > erosion_limit`.
5. Emit one `structural-erosion` finding when `erosion delta > delta_limit`.
6. Merge the two triggers into one finding if both apply.
7. Include base ratio, head ratio, delta, cutoff, and configured limits.
8. Include at most `top_contributors` deterministic contributor records.
9. Apply normal suppression and severity handling.

The finding location should be the highest-ranked contributor. If no contributor
exists for an absolute-limit finding, use the repository-level location already
used for aggregate findings. The finding must not be emitted when the rule is
`off`.

Rank contributors by descending mass increase, then descending head mass, then
repository-relative path, declaration location, and qualified name. Use the
same ordering in all report formats.

The rule must not fail `check` for warning findings. An error-severity finding
returns exit code `1`; configuration, Git, analyzer, and artifact failures
return exit code `2`.

## Deterministic scenarios

### Scenario 1: no erosion change

Given base and head summaries have equal erosion ratios.
When `check` evaluates `structural-erosion`.
Then no delta finding is emitted.

### Scenario 2: absolute threshold

Given the head erosion ratio is greater than `erosion_limit`.
When `check` evaluates the rule.
Then one finding reports the absolute-threshold violation.

### Scenario 3: delta threshold

Given the head ratio minus the base ratio is greater than `delta_limit`.
When `check` evaluates the rule.
Then one finding reports the erosion increase.

### Scenario 4: both thresholds

Given both threshold predicates are true.
When `check` evaluates the rule.
Then exactly one finding is emitted with both predicates represented in its
machine-readable properties.

### Scenario 5: refactoring into helpers

Given a change moves decision logic from one function into several helpers.
When the head summary is computed.
Then the ratio is computed from the resulting head functions without assuming
that extraction is either good or bad.

### Scenario 6: excluded or generated code

Given a path is excluded by the existing scope rules.
When either revision is analyzed.
Then its functions do not affect total mass, high-complexity mass, or findings.

### Scenario 7: malformed source

Given a changed Rust file cannot be analyzed in the head revision.
When `check` runs.
Then the existing malformed-source behavior applies and the erosion result is
not presented as complete evidence.

### Scenario 8: incompatible artifact

Given the artifact uses a different analyzer version, cutoff, or policy
fingerprint.
When `check` starts.
Then it exits `2` with an actionable rebuild-artifact message.

## History view

Add a read-only command or mode that accepts an explicit ordered revision
range and prints one summary per revision. The exact CLI spelling is an
implementation decision, but the release contract must define it before
implementation. It must not silently walk an unbounded repository history.

Required behavior:

- accept an explicit revision range or a start revision plus `--count`;
- analyze immutable Git revisions only;
- reuse the same scope, analyzer version, and cutoff for every revision;
- report commit ID, total mass, erosion ratio, high-complexity count, maximum
  CC, and maximum mass;
- support `human` and `json` output;
- sort revisions in chronological order unless the command documents another
  order;
- return exit code `2` for invalid revisions or inconsistent analyzer inputs;
- avoid treating trend output as a gate finding.

History mode should not require prebuilt artifacts in v0.4. If performance
requires artifacts later, that change needs a separate compatibility contract.

## Calibration

Before release:

1. Select at least 20 maintained Rust repositories with varied sizes.
2. Sample history windows with known refactors and feature additions.
3. Record erosion ratios, deltas, contributor stability, and false-positive
   classifications.
4. Compare the default cutoff of `10` with at least one lower and one higher
   cutoff.
5. Set provisional defaults from observed distributions, not from the paper's
   Python measurements alone.
6. Keep the rule warning-only unless the false-positive rate and reviewer
   actionability meet the project's existing calibration standard.
7. Record the data and decision in `docs/EROSION-CALIBRATION-REPORT.md`.

The paper motivates this work but does not establish Rust thresholds. Its
reported human-repository erosion averages vary by repository group, which is
evidence for calibration rather than a universal limit.

## Implementation phases

### P9.0: summary facts

- Extract repository summaries from existing function records.
- Add schema and fingerprint handling.
- Add artifact serialization tests and deterministic ordering tests.

### P9.1: erosion rule

- Add configuration parsing and validation.
- Compare base and head summaries.
- Add findings, suppression handling, and all report formats.
- Add unit and temporary-repository integration tests.

### P9.2: attribution

- Define contributor matching for moved, deleted, and extracted functions.
- Implement stable ranking and bounded output.
- Add evidence to human, JSON, and SARIF reports.

### P9.3: history view

- Finalize the CLI contract.
- Analyze bounded immutable revision sequences.
- Add JSON schema tests and invalid-range tests.

### P9.4: calibration and release

- Run the Rust repository calibration.
- Publish the calibration report.
- Update README, `HANDOFF.md`, and the agent skill.
- Run the complete validation suite.

## Acceptance criteria

| Area | Criterion |
| --- | --- |
| Compatibility | Existing v0.3 behavior remains unchanged when the new rule is absent or `off`. |
| Correctness | Artifact and head summaries use identical analyzer scope and cutoff. |
| Determinism | Identical revisions, policy, and inputs produce byte-identical JSON and SARIF. |
| Bounded output | A finding reports no more than `top_contributors` contributors. |
| Attribution | Contributor ordering is stable across runs and formats. |
| Safety | Warning-only defaults never produce exit code `1`. |
| Failure handling | Invalid configuration, revisions, artifacts, and analyzer mismatches produce exit code `2`. |
| Calibration | Rust calibration data and threshold decisions are documented before release. |
| Quality | `cargo fmt --check`, `cargo clippy --all-targets --all-features --locked -- -D warnings`, `cargo test --locked`, `RUSTDOCFLAGS='-D warnings' cargo doc --no-deps`, `cargo audit`, and `git diff --check` pass. |

## Design risks

1. A ratio can improve because low-complexity code was added, without any
   refactoring benefit. Report absolute mass and ratio together.
2. A ratio can worsen after a legitimate centralization. Keep the rule warning-only
   and expose contributors.
3. Function identity can change during extraction or movement. Use the existing
   head-surviving declaration model and treat attribution as evidence, not exact
   lineage.
4. Generated or test-heavy repositories can distort totals. Reuse scope rules
   and calibrate on repository classes that users will actually gate.
5. Recomputing many revisions can be expensive. Bound history input and measure
   performance before adding artifact caching.

6. Near-clone matching currently reports intentional duplication of small
   private utilities. Consolidate obviously shared utilities when practical,
   but defer size-aware utility filtering or intent-aware clone classification
   until a calibrated rule design exists.

## Non-goals for v0.4

- Do not claim that a high erosion ratio proves poor design.
- Do not promote the rule to an error by default.
- Do not add a generic "AI slop" score.
- Do not add semantic or language-model analysis.
- Do not change near-clone matching thresholds as part of this plan.
